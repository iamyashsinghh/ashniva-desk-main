Design principles that shape everything below

  1. Task activity is the report. Nobody writes a status update twice. Completing a task asks four things; daily reports and the client's "Completed Today" are derived.
  2. Internal vs client-visible is a first-class flag on every comment, update, attachment and estimate — shown as a badge in the UI, enforced in the API by a visibility filter, not by the frontend.
  3. Tenant isolation at the query layer. Every tenant-scoped table carries organization_id; a Prisma middleware injects it from the JWT on every read/write. Clients never hit internal endpoints.
  4. Two hats for seniors. Every task has a category (Development, Management, Review, Testing, Planning, Client Meeting …). Managers get real assignable tasks too. "My Tasks Today" shows Management and Development in separate sections; reports split on the same field. Admin can hide a user's Development section with a per-user flag — no new role.
  5. Nobody publishes by marking a task done. Completion is the end of a gated chain: code review → automated checks → QA on staging → optional client UAT → controlled release → live verification. See §11.
  6. Minimal fields, fixed workflows. No custom fields, no custom workflows, no per-project statuses in Phase 1–2.

1. User flows

1.1 Developer — daily loop

  1. Sign in → Developer dashboard: Today's tasks, overdue, awaiting my review fixes, tickets assigned to me.
  2. Open task → Start Work (Assigned → In Progress; timer optional). Branch AD-124-login-otp auto-links via GitHub.
  3. Working: internal comments, Blocked with reason (notifies senior). Commits with AD-124 attach automatically.
  4. Development Completed sheet (what was done · time · client-visible?) → opens/links PR → senior gets a Review task → Code Review.
  5. Review approved + mandatory checks green → Ready for QA → staging deploy → Send for Testing (confirm tester) → QA assignment created with auto-selected test account.
  6. QA Passed → (Client UAT if enabled) → Ready to Publish → added to a Release → Published Live → Live Verification → Completed. QA Failed returns to developer with reason + evidence; Fix Submitted → Retest.
  7. Daily report for the developer is generated automatically at 18:30 IST (and viewable live).

1.2 Senior / Team Lead — managing and building

  1. Senior dashboard: Pending reviews · team board summary · blocked · overdue · my own tasks (separate panel).
  2. Create Task (title, project, assignee, priority, due date — everything else optional) or Assign an unassigned task/ticket-task.
  3. Review queue: open task → see completion summary, diff of files/links → Approve or Reject with Comment.
  4. If the update is client-visible: Publish Update (or edit wording first) → appears in client portal "Completed Today".
  5. Own development work follows flow 1.1; logged as DEVELOPMENT and shown separately in the senior report.

1.3 Client — raise a ticket and follow progress

  1. Sign in → Client dashboard: In progress · Completed today · This week · Open tickets · Pending decisions · Support hours.
  2. Raise Ticket: type, title, description, screenshot. Ticket number auto-generated; SLA clock starts.
  3. Ticket replies: sees public replies only; can reply, attach, and mark "Waiting for Client" items as answered.
  4. Approvals: files or decisions requiring approval → Approve / Request changes.
  5. Project detail (client view): milestones, progress, published updates, releases, contract hours.

1.4 Support Executive — ticket triage

  1. Ticket list filtered New / SLA at risk.
  2. Triage: set type, priority, product, assign to team/developer → Assigned.
  3. Reply publicly or comment internally; set Waiting for Client when blocked on requester.
  4. Convert to Task(s): one or many development tasks linked to the ticket; ticket status follows the tasks.
  5. Resolve with resolution summary → Resolved. Auto-closes after 5 days without reopen.

1.5 Ticket → Task linkage

Ticket and tasks stay linked via task.ticket_id. When all linked tasks are Completed, the ticket moves to Review/Testing and the support executive is prompted to verify and resolve. Client-visible task updates on ticket-linked tasks post as public ticket replies (after approval).

Cross-cutting

  • Events: NestJS EventEmitter2 in-process; side effects that need retry (email, WhatsApp, report snapshots, SLA checks) are enqueued to BullMQ.
  • Real-time: Socket.IO gateway; rooms per org:{id}, project:{id}, user:{id}. Events: task.updated, ticket.replied, notification.new.
  • Jobs: sla-monitor (every 5 min), due-date-reminders (08:00 IST), daily-report-snapshot (18:30 IST), contract-expiry (daily), ticket-auto-close (daily), notification-digest.
  • Branding: organization_settings.branding JSON {logoFileId, primary, secondary, accent, productName}. Frontend fetches /branding (public, by host or org) and sets CSS variables on :root. Nothing else in the codebase references a colour literal.

11. Development, QA and release workflow

One fixed state machine for development-kind tasks. Admin can rename labels, not add states. Management-kind tasks use the short path (Assigned → In Progress → Completed).

Happy path
  ASSIGNED → IN_PROGRESS → DEV_COMPLETED → CODE_REVIEW → READY_FOR_QA → TESTING_STAGING → QA_PASSED
           → [CLIENT_UAT if project/release requires] → READY_TO_PUBLISH → PUBLISHED_LIVE → LIVE_VERIFICATION → COMPLETED
Gates (enforced in task-workflow.ts, not the UI)
  DEV_COMPLETED → CODE_REVIEW      requires linked PR (or manual link) ; creates a Review task for reviewer_id
  CODE_REVIEW → READY_FOR_QA       requires review APPROVED  AND  all required_checks = success (or check_override with reason by PM/Lead)
  READY_FOR_QA → TESTING_STAGING   requires staging deployment success for the PR head SHA (webhook) or manual staging URL by dev/manager
                                   → "Send for Testing": confirm tester → testing_assignment(QA) + credential grant
  QA_PASSED → READY_TO_PUBLISH     skips UAT unless requires_uat ; UAT approval by client required otherwise
  READY_TO_PUBLISH → PUBLISHED_LIVE only via a Release publish by a user in project_release_policy.publishers
  PUBLISHED_LIVE → COMPLETED       only after LIVE_VERIFICATION assignment result = PASS ; then linked tickets → RESOLVED
Failure paths
  TESTING_STAGING → QA_FAILED → RETURNED_TO_DEV (auto, carries reason + evidence) → FIX_SUBMITTED → TESTING_STAGING (RETEST assignment)
  CODE_REVIEW: changes requested → RETURNED_TO_DEV
  LIVE_VERIFICATION → LIVE_FAILED → ROLLBACK_REQUIRED (release.rollback or hotfix task) → FIX_SUBMITTED → … → republish
Side states: BLOCKED (from any active state, returns to previous), CANCELLED, DRAFT (unsaved create form)

13. QA, test environments and test accounts

  • Tester dashboard views: Assigned to Me · Ready for Testing · Testing Today · Failed & Returned · Waiting for Retest · Passed Today · Client UAT Pending · Live Verification Pending · Overdue Tests.
  • Assignment carries: task + ticket, project, what was developed, what to test, acceptance criteria, staging URL, test account (grant), browser/device requirements, developer notes, PR link, checks/build result, deadline.
  • Test form: Pass/Fail · environment · what was tested · actual result · failure description · browser/device · evidence · comment for developer · retest required · severity (if failed). One-click: Start Testing · Pass · Fail & Return · Request Clarification · Retest · Verify Live. Fail auto-returns the task with reason + evidence and notifies the developer.
  • Test accounts: created once per project per role (Test Super Admin, Test Admin, Test Manager, Test Employee, Test Customer, Test Vendor, custom). Secrets encrypted at rest (envelope encryption, key in KMS/env, never in DB plaintext). On Send for Testing the system picks the account matching the task's target role (fallback: developer picks). Tester gets a credential grant (default 8h TTL): "Generate temporary access" → "Reveal" (masked, copy button, 60s visible) — every generate/reveal/rotate/revoke is written to credential_access_log. Rotation after test (policy), optional data-reset hook. Passwords never appear in notifications, comments, emails, WhatsApp or commits; notifications carry a secure link only. Manual credentials only via "Special account for this test" (also encrypted, single-use).
  • Live verification: publishing creates a LIVE_VERIFICATION assignment (production, smoke checklist from the release). Pass → release VERIFIED → tasks COMPLETED → tickets RESOLVED. Fail → release FAILED → rollback/hotfix flow.

14. GitHub integration

  • GitHub App (one app, installed per GitHub org; installation token per request, least-privilege: contents:read, pull_requests:read, checks:read, deployments:read+write, metadata:read, actions:read; write only for workflow_dispatch on release). No shared PAT.
  • Webhooks: HMAC-SHA256 signature verified against per-app secret; X-GitHub-Delivery stored in webhook_events (unique) → duplicates dropped; processing in BullMQ with retries. Events: push, pull_request, pull_request_review, check_suite/check_run, workflow_run, deployment_status, release.
  • Linking: regex AD-\d+ in branch name, commit message, PR title/body → github_refs rows on the task. Per project mapping: repo, default/dev/staging/prod branches, staging/prod environment names, required check names.
  • Task shows: repo, branch, latest commits, PR (state, reviewer, merge status), checks (Pending/Running/Passed/Failed/Cancelled), staging & production deployments. Review comments stay in GitHub; status mirrored.
  • Gating: Ready for QA blocked while any required check ≠ success, unless an authorized manager records an override reason (audited). Automated checks never replace manual QA.

15. Releases and live publishing

  • Release = version + project + included tasks/tickets/PRs + staging URL + branch/tag + checks + QA results + UAT status + planned time + approvals + publisher + production URL + deployment result + rollback version + notes (internal, client).
  • Actions: Create Release · Add Task · Request Approval · Schedule Publishing · Publish to Production · Verify Live · Roll Back. Publish requires all project_release_policy.approvers decisions = APPROVED, all items QA_PASSED (and UAT approved if required), and actor ∈ publishers. Publishing dispatches the production workflow (GitHub) or records a manual deploy; confirmation modal requires typing the version.
  • Rollback records target version, reason, and reopens live-verification.

  1. Client: Home → Raise ticket (product, module, title, description, urgency, business impact, evidence incl. voice note; "Request a call now / schedule callback") → ticket auto-routed → status + public replies + call history → Reopen or Confirm resolved.
  2. Developer: push "New ticket auto-assigned" → Incoming alert (Accept · View · Snooze 5 min) → Support queue with SLA countdown → Accept → Start work (linked task) → Call through IVR / request callback → public reply or internal note → evidence → Link commit/branch/PR → Send for review → staging → Send for testing. Duplicate warning → Confirm duplicate / Link problem / Create problem (suggest; senior/support confirms). Escalate to senior.
  3. Senior / Manager: Escalation queue (unacknowledged, SLA risk, L1/L2) → Team availability (available · busy · absent · on-call) → Reassign with reason → Call client → Group into Problem → Ask developer → Request/review RCA → Approve emergency fix → Approve release / publish → Recurring issues; support work shown separately from development tasks.
  4. Tester: QA queue → Test detail (staging URL, temporary access, acceptance criteria, checklist, previous failures, build/PR) → Start · Pass · Fail with reason + evidence (auto-returns) → Approve for release → Live smoke test after production.
  5. Support executive: non-technical queue (training, account, access, billing) → reply / resolve; "Route to developer" hands a technical issue to automatic routing.
  6. Admin (mobile-lite): primary/backup mapping, module ownership, on-call, SLA & escalation rules, routing status, IVR health; everything else on desktop.
  7. IVR: identify caller → open/create ticket → find responsible/on-call developer → app screen-pop with context → Tata IVR bridges both parties (numbers hidden) → unanswered → backup → senior → callback queue → call time, duration, result, recording ref and notes saved on the ticket. The app never dials directly; every call is initiated by the backend through the configured provider, and is disabled offline.
